## 2. 먼저 고칠 공통 문제

### 2.1 사진과 비교할 수 있는 카메라가 필요하다

현재 `AppendixGSceneCfg.review_cam`은 모든 task에 동일한 높은 시점이다. 논문 사진은 낮은 정면, 비스듬한 측면, 위에서 내려다보는 시점이 섞여 있다. 현재 이미지에서는 테이블과 로봇이 크게 보이고 대상 물체가 작아져, 크기·앞뒤·회전을 정확히 비교하기 어렵다.

Luna 구현 지침:

1. task별 `reference_camera` 설정을 추가한다. 테이블 모서리, 테이프 사각형, 기구의 수직선 등으로 시점·프레이밍을 먼저 맞춘다.
2. 높이·시선 방향·초점거리를 조정하고, 같은 task에서 카메라를 고정한 다음 물체 배치를 맞춘다. 사진 일치를 위해 카메라와 물체를 동시에 계속 움직이지 않는다.
3. 사진에 보이는 좌우/앞뒤를 월드 X/Y와 동일시하지 않는다. 사진 속 좌표와 테이블 평면 좌표의 대응을 저장한다.
4. S15처럼 이미지 자체의 방향이 다른 경우 원본 방향과 비교용 회전을 기록한다. 모든 사진을 일괄 회전하지 않는다.
5. 출력은 `논문 / reference_camera / policy 외부 카메라` 1×3 비교와, 기존 top-down review·wrist 원본 이미지를 제공한다.
6. reference camera의 보정값은 사진으로 추정한 값이다. 정책 입력 카메라를 바꾸는 경우에는 별도 실험 설정으로 기록하고 두 모델에 동일하게 적용한다.

### 2.2 물체별로 정확한 형태와 시작 관계를 정의해야 한다

컵 안의 마커, 서랍 위에 걸친 모자, 포개진 컵, 세워진 트레이처럼 **관계와 시작 상태 자체가 과업의 일부**다. 물체 이름과 색만 같아서는 부족하다.

task별 reference specification에 다음을 저장한다:

- 물체별 ID·역할: 조작 대상 / 목표 용기 / 고정 기구 / distractor.
- 눈에 보이는 실루엣, 색, 물체 수, 주축 방향, 가로:세로:높이 비율.
- 사진상의 중심·바운딩박스·접촉점·개구부·레버 위치. 정규화 좌표와 신뢰도를 함께 기록.
- `inside`, `on`, `leaning_on`, `in_front_of`, `left_of`, `open`, `nested` 등의 관계.
- 보이지 않지만 task에 필요한 물체와 그 배치 가정. 예: S18 사진에서 별도 빵의 초기 위치는 명확하지 않다.
- task 시작 시 이미 목표가 달성돼 있지 않은지, 조작을 막는 가림이나 충돌이 생기지 않는지.

사진 배치에 대한 목표치와 월드 XYZ는 구분한다. 사진에서 보이는 물체 간 크기 비율을 먼저 맞추고, 알려진 로봇/테이블 크기로 실제 치수의 타당성을 검사한다.

### 2.3 에셋 선정과 가져오기 과정 모두 개선해야 한다

코드에서 확인한 내용:

- `_define_external_glb_visual()`은 `scale = size / source_span`으로 축마다 다른 배율을 적용한다. 원래 비율이 다른 에셋을 지정한 박스에 맞추면 눌리거나 늘어날 수 있다.
- GLB의 vertex normal, base color, roughness/metallic **상수 값**은 현재 가져온다. 하지만 GLB의 normal texture, metallic-roughness texture, occlusion, transmission 등의 처리 경로는 이 함수에서 확인되지 않는다. 모든 에셋에 해당 맵이 들어 있다는 뜻은 아니다.
- `_bind_obj_texture()`에는 normal map 연결 기능이 있으나, GLB importer는 이를 전달하지 않는다. 텍스처의 색 공간도 명시적으로 설정하지 않는다.
- 여러 procedural 물체는 `displayColor` 위주다. 종이·천·금속·식품의 표면 차이가 부족하다.
- YAML의 `appearance`, `asset`, `template_ref`가 실제 출력과 어긋날 수 있다. U01의 에셋 후보 설명과 실제 cup template, U02의 둥근 사각 접시 설명과 다각형 출력이 예다. 선언한 필드가 builder에서 소비되는지 확인해야 한다.

개선 방법:

1. silhouette와 기능 구조가 비슷한 에셋을 고른다. 무료 여부·파일 형식만 보고 채택하지 않는다.
2. 기본 배율은 등방 스케일로 하고, 비등방 스케일은 의도·축별 배율을 기록한 예외로 둔다. 비율이 크게 다르면 교체 또는 모델링한다.
3. 중요한 개구부·서랍·손잡이·레버는 모델에 실제로 있어야 한다. 어두운 원을 그려 구멍처럼 보이게 하는 방식은 조작 대상에 사용하지 않는다.
4. 기존 USD 재질을 보존하거나 GLB의 실제 material channel을 변환한다. normal은 raw/linear, base color는 적절한 색 공간으로 처리하고 렌더에서 확인한다. normal의 Y 방향과 UV 방향도 점검한다.
5. 물체의 실루엣·크기를 맞춘 후 normal/roughness/미세 질감을 붙인다. 작은 컵 무늬만 고치고 잘못된 컵 비율을 남겨두지 않는다.
6. 신규 에셋은 후보 미리보기·원본 링크·재배포 조건·파일 hash·변환 내역을 기록한다. 여기서는 신규 에셋 채택을 확정하지 않았다.

### 2.4 조명·배경 차이를 별도로 보정한다

현재 Appendix 환경은 기존 DROID의 로봇·카메라와 `SphereLight(intensity=5000)`를 상속한다. 생성 USD에는 texture 없는 dome light(intensity 500)가 있고, 모든 task에 같은 밝은 목재 상판을 사용한다. 참조 사진은 더 짙은 목재, 흰 벽 또는 회색 칸막이 등 배경이 다르다. 회색 칸막이는 현재 builder에서 S01/S02에만 추가된다.

이것은 코드상 확인한 차이다. 현재 화면이 밝고 평평하게 보이는 원인을 조명 한 가지로 단정하거나, upstream과 다른 렌더 엔진이라고 단정하지 않는다.

Luna는 동일 geometry·camera로 A/B 렌더를 만든다:

- 현재 조명 → 사진에 맞춘 광원 방향/크기/세기, 노출·톤 매핑.
- 같은 조명 아래 neutral gray 물체와 흰 컵으로 색 관리 확인.
- 목재의 색·결 방향·텍스처 반복 크기·거칠기를 조정.
- 금속의 반사, 유리의 외곽·두께, 천의 거칠기를 각각 확인.
- 사진별로 흰 벽/회색 칸막이/테이프 위치를 맞춘다. 모든 장면에 같은 배경을 강제하지 않는다.

대표 task에서 개선을 확인한 설정만 공통화한다. 최종 검토 이미지는 실제 평가에 쓰는 Isaac 장면에서 출력한다.

## 6. 완료 기준

아래 수치는 작업자가 참고할 **제안 기준**이며 논문에 나온 값이나 현재 측정 결과가 아니다. 저해상도 사진에서 불명확한 항목은 수치 통과로 처리하지 말고 confidence와 수동 검토를 기록한다.

### 장면 이미지 승인

- [ ] 명확하게 보이는 물체의 종류·수·주요 색·열림 상태가 일치. 근거 없이 추가/삭제한 물체 없음.
- [ ] task 핵심 부품(컵 손잡이, 레버, 구멍, 서랍 입구 등)이 실제로 식별됨.
- [ ] 포함·중첩·지지·접촉·앞뒤 관계가 모두 일치.
- [ ] 보정한 reference camera에서 주요 중심 위치 오차가 화면 대각선의 약 5% 이내, 물체 간 크기 비율 오차가 약 15% 이내를 초기 목표로 삼음. 가림/원근/annotation 불확실성도 저장.
- [ ] 길쭉한 물체는 사진상의 주축과 약 10° 이내를 초기 목표로 함. 원형·정면 물체에는 적용하지 않음.
- [ ] 배경과 상판 색/결/프레이밍, 광원 방향과 그림자가 task를 다르게 보이게 하지 않음.
- [ ] 근접 컷뿐 아니라 실제 policy camera 해상도에서도 물체와 주요 부품이 식별됨.
- [ ] 이미지·USD·설정·에셋의 revision/hash가 맞음. 오래된 render를 새 코드의 결과로 표기하지 않음.

### rollout 이전 검사

- [ ] 열린 용기의 collider가 내부를 막지 않고, 실제 grasp 부위와 visual/collision이 맞음.
- [ ] policy-free settling 전후 상태를 비교해 부유·관통·전도·초기 물체 이탈이 없음.
- [ ] 여러 번 reset해 동일 seed/layout에서 동일 상태가 재현됨.
- [ ] 레버/서랍/키/문은 필요한 자유도·한계·접촉 event가 있고 관측 가능한 상태로 기록됨.
- [ ] task success가 root distance 하나가 아닌 실제 필요한 관계·순서·접촉 상태를 측정함.
- [ ] 절단·cinch·분사·wire weaving·조리 등은 실제 구현한 상호작용 범위를 명시. 정적 시각 모델만 있는 task는 해당 동작 검증 완료로 표시하지 않음.

시각적 유사성은 실행 가능한 동일 과업을 만드는 필요 조건이다. 이 검사만으로 논문과 동일한 물리 조건이나 성공률을 보장하지 않는다.

## 7. 병렬 작업과 산출물 관리

- CPU에서 reference annotation, 에셋 탐색/정리, mesh/texture 준비는 병렬화할 수 있다. 작업자를 task 번호보다 공유 에셋 묶음으로 배정한다.
- 공통 builder/camera/material 파일은 한 통합 작업자가 관리한다. 여러 작업자가 같은 함수를 동시에 고치지 않는다.
- 현재 기록상 S02→S07를 같은 Isaac 세션에서 열던 실행은 완료되지 않았고 S07 단독 실행은 완료됐다. 정확한 원인은 확정되지 않았다. 기본 렌더는 **task/layout당 독립 프로세스**로 한다.
- 렌더 2개 병렬은 GPU별 단독 배정, 메모리·CPU thread·프로세스 수, 결과 파일 격리를 확인한 뒤 대표 장면 2개로 검증한다. GPU가 2개 있다는 사실만으로 안정성을 가정하지 않는다.
- 새 출력은 `pose_review_quality_v7`처럼 별도 디렉터리에 저장한다. v6와 비교 가능해야 한다.
- 각 출력에 task/layout, config hash, asset hash, camera/light profile, build/render 시각, 검토 결과를 manifest로 남긴다.
- 상태는 `draft → geometry_reviewed → appearance_reviewed → physics_validated → user_approved`로 관리한다. 이미지 생성 자체는 승인과 다르다.

## 8. 기존 문서에서 바로잡아야 할 부분

- group_c U02 README의 '별도 부채가 없다'는 해석은 현재 참조 사진 및 생성된 부채와 충돌한다.
- group_c U10의 '이미지 매핑 미해결' 메모는 갱신해야 한다. Appendix G(b)의 U10 행이 현재 사진을 직접 연결한다. 남은 미확인은 작은 부품의 식별과 과업의 구체적 수행 방식이다.
- group_c U09의 '트레이가 테이블에 눕는다'는 설명은 원본 사진의 upright 상태와 다르다.
- task별 후보 에셋, 실제 사용한 에셋, procedural fallback을 명확히 구분한다.
- S07의 기존 readiness blocker처럼 이미 구현한 내용과 오래된 메모가 충돌하는 곳은 실제 코드·렌더 기준으로 갱신한다.
